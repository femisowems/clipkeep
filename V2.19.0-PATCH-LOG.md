## 1. Origin

1. **Femi's question (Nov 25, 2026, ~8:11 AM EST):** "For clipkeep is there a time duration for it?" — i.e. how long are clips kept? The code's answer: no time dimension at all. Unpinned, unboarded clips survive until the count cap (`historyLimit`, default 200, 0 = unlimited) pushes the oldest out; pinned and boarded clips never expire. How long a regular clip lasts therefore depends entirely on copy volume.
2. **The improvement plan (same morning):** Edison proposed three options — (1) add a keep-for period alongside the cap, (2) replace the cap with a period, (3) secret auto-expire first (roadmap #5). Recommendation was **1**, with 3 as a follow-up patch. Femi: "Your recommendation is a solid plan, thanks."
3. **Scope addition (Nov 25, later that morning, Femi's approval):** a storage readout in Settings (clip count + on-disk size, kept current), a "Purge older clips" one-off button, and a "Clear all unpinned history" button with confirmation. The third item turned out to already exist — see §3, S3.

## 2. Pre-existing behaviour the feature builds on

- `ClipStore.historyLimit` (main.swift): a UserDefaults-backed computed property; the setter writes the default, then `trim(); save()`. `trim()` walks `items` (newest first), always keeps `isKeeper` clips (pinned || boarded), keeps unpinned clips up to the cap, and removes the rest via `recordTombstone(item)` + `deleteImageFile(of:)` — the schema-v2 deletion path from v2.17.0, so trims propagate as sync tombstones (kept 30 days, `purgedTombstones` at load).
- `trim()` is called from `insert()` (every capture) and from the `historyLimit` setter. It is NOT called at launch — fine for a count cap (a saved history can never exceed the cap it was saved under), but an age limit is different: time passes while the app is closed.
- Settings → General already hosts the History limit popup (`settingsLimitPopup`, items 200/500/1000/No limit with Int `representedObject`s), wired via `settingsLimitChanged` → `limitChosen(_:)` (an NSMenuItem-shaped handler shared with the ••• submenu), and `syncSettingsControls()` re-selects the live value whenever Settings is shown or regains key status.
- The Clear History button (Settings → General and the ••• menu) has, since v2.15.5, shown a confirmation alert and deleted exactly the unpinned/unboarded clips via `store.clearHistory()` — keepers kept, tombstones recorded.

## 3. The changes

All in `main.swift` unless noted. Two commits: `d6e3c5d` (R1–R4 + tests + SPEC + build.sh) and `a780726` (S1–S2 + tests).

### Retention (commit `d6e3c5d`)

- **R1 — `ClipStore.retentionDays`.** A UserDefaults-backed Int beside `historyLimit`, key `retentionDays`, default 0 = keep forever. Setter mirrors the pattern exactly: write, `trim()`, `save()`. Because the default is Forever, upgrading changes nothing until a user opts in.
- **R2 — `ClipStore.isPastRetention(_:retentionDays:now:)`.** A static pure test beside `purgedTombstones`: false when the period is 0 or the clip is a keeper; otherwise `now - createdAt > days * 86_400`. Age is measured from **creation** (`createdAt`), not `effectiveUpdatedAt` — a clip's keep-for clock starts when it was copied, and pinning/editing a clip must not silently extend (or shorten) its life; keepers are exempt outright.
- **R3 — `trim()` prunes on either limit.** The guard becomes `limit > 0 || days > 0`; each non-keeper is first tested against `isPastRetention`, then against the count cap. Both removal branches use the identical `recordTombstone` + `deleteImageFile` path, so a retention deletion is indistinguishable from a count trim or a manual delete downstream (tombstone stamped with the deletion time, image file removed, 30-day tombstone retention unchanged). Age-expired clips don't consume count-cap slots.
- **R4 — Launch sweep.** `ClipStore.init` runs `trim()` once after `load()` and saves only if something was pruned. This is the one genuinely new call site: without it, clips that cross the window while the app is closed would linger until the next capture. With the default (Forever) and a within-cap history it is a no-op walk.
- **R5 — Settings UI.** A "Keep clips for:" popup directly under the History limit row, same row shape and wiring: items Forever / 7 days / 30 days / 90 days / 180 days / 1 year with Int `representedObject`s (0/7/30/90/180/365), `settingsRetentionChanged` → `retentionChosen(_:)` (the `limitChosen` twin), `settingsRetentionPopup` re-selected in `syncSettingsControls()`. The ••• menu does NOT gain a retention submenu — the spec scoped this to Settings.
- **R6 — Version + spec.** `build.sh` stamps 2.19.0 (both plist keys). SPEC.md gains item 10 (retention period) and lists retention among the UserDefaults settings.

### Storage & purge (commit `a780726`, the scope addition)

- **S1 — Storage readout.** `ClipStore.diskUsageBytes` sums the history file's size plus every file in the images folder. Settings → General shows "History: N clips · X on disk" (`storageSummaryText()`, `ByteCountFormatter` file style) in a secondary-colour 12pt label under the retention row. It refreshes in `syncSettingsControls()` (Settings shown / regains key), immediately after a retention change (which trims), and after a purge.
- **S2 — Purge Older Clips button.** `ClipStore.purgePastRetention()` walks the live list once and removes every past-period clip through the same tombstone path, returning the count; at Forever it returns 0 without touching anything. The button disables at Forever with a tooltip explaining why ("Choose a keep-for period above to purge clips by age") — state kept live by `refreshPurgeButton()` from both `syncSettingsControls()` and the retention-change handler. After a purge, the readout line reports the outcome ("Purged N clips older than D days — History: …" / "Nothing older than D days to purge — …") so the click never feels dead (the v2.18.1 lesson); the next Settings sync restores the plain summary.
- **S3 — "Clear all unpinned history": already shipped, no duplicate added.** The scoped item describes the existing Clear History control exactly — confirmation alert ("All unpinned clips will be deleted… Pinned and boarded clips are kept. This can't be undone."), `store.clearHistory()` tombstoning every non-keeper. Adding a second button doing the same thing would be clutter, so none was added; checklist step 29 re-verifies the existing control instead.

### Tests (tests.swift, +16 checks → 96)

Retention: default is Forever; the age test at 31 vs 30 days, inside-window at 1 day, Forever never expires, pinned and boarded exemptions; end-to-end through the store — opting into 30 days prunes a 40-day-old clip on insert *with a tombstone*, keeps a 2-day-old clip and a 40-day-old pinned clip. Purge: staged list (set directly on the store, since every automatic path already trims) — exactly the one past-period unpinned clip is removed and tombstoned, fresh + pinned stay, Forever purges nothing. Storage: after `saveNow()`, `diskUsageBytes > 0`.

## 5. Rollback & release notes

- The release ships through the standard pipeline: push via `push-files` → CI → download artifact → publish the **inner** `ClipKeep.zip` (with `ClipKeep.app/` at its root — never the raw artifact download) as `ClipKeep-app-v2.19.0.zip` → bump gist feed `114759138a0c643983d577960363096a` (both `latest` and `version` keys, `sha256` of the inner zip, revision 43 → 44) → docs commit (README + ROADMAP + this log).
- The in-app installer keeps a backup of the previous bundle and rolls back automatically if the swap fails.
- If v2.19.0 misbehaves in a way the installer can't handle: the v2.18.1 release asset remains on GitHub (https://github.com/femisowems/clipkeep/releases/tag/v2.18.1) — re-pointing the feed's `url`/`sha256` back to it and bumping `revision` returns every updater to v2.18.1. Source-level, the feature is two commits (`d6e3c5d`, `a780726`) and reverts cleanly with `git revert`.
- Data safety: the release adds one UserDefaults key and no schema change (history file stays schema v2). The only destructive path is retention itself, and only after a user opts into a period — at the Forever default nothing is ever pruned by age. Highest-risk item if something looks wrong after shipping: **R4** (the launch sweep) — it is the only trim that runs without a user action in the room; check it first if clips vanish unexpectedly after a relaunch with a period set.
